# AERO Brief 任务确认 · v1.0

让没参与讨论的人也能准确说出客户要我们做什么、各项工作要达到什么目的、有什么明确条件。统一判断方法，不统一项目答案。

执行前读 [产出标准](references/output-standard.md)。完整记录使用 [任务模板](assets/brief-review-template.md)；措辞含混时读 [语言与意图分析](references/brief-language-reading.md)；迁移参考 [不同委托示例](references/task-confirmation-examples.md)。

## 五步形成任务确认

### 1. 找到有效输入
读原始 Brief、附件与已确认补充，保留页码或出处。确认委托是提案、策略、制作执行还是既有方案适配。区分客户要求、客户对市场的判断、我方建议与未知；版本冲突不暗自选边。没有读到的附件不算已知。

### 2. 把要求分清
内部识别背景、目标对象、期望变化、交付物、硬条件、偏好建议和评价要求。分析“必须／希望／建议”“不是……而是……”、强调与限定范围，判断各句话约束哪项工作。重复不等于最高优先级；局部要求不能扩大到全案。

从语言线索提出可能的意图解释，同时检查其他解释；不能以心理学名义读心。未确认的意图推断单列，不能作为明确需求放进摘要。

### 3. 给每项交付配上目的
内部建立“任务编号 → 交付 → 要解决或表达什么 → 明确条件 → 来源”的对应关系：
- 为什么发起这项工作？希望影响谁、改变什么？
- 实际购买什么成果或服务？每项分别承担什么任务？
- 哪些必须配套，哪些只是可选手段？

不强行给不同交付找唯一洞察，不把“提案包含制作建议”改成“承诺制作”。检查冲突、遗漏和目标关系；独立判断可以是识别任务分工，不必制造新问题。

### 4. 压成准确的人话
优先输出一句任务确认，句型只作辅助：

> 客户要〔委托成果〕：〔核心工作 A〕用于〔具体目的 A〕，〔工作 B〕用于〔具体目的 B〕，并提供〔必需配套〕。

只保留会改变任务理解的对象、市场、资源和条件。品牌名、代言人、TVC、预算、销售指标、整合营销不是固定槽位。原文只有目标而没指定形式时，保持形式开放，不能替客户选媒介。

精确优先于长度。复杂任务可用一句总述加任务表；不得为压缩遗漏独立任务。用户只问一句话就只给一句；存在实质缺口时附最少必要待确认，不假装完整。

避免用“提升品牌力、打造影响力、让人记住并购买”等通用结果取代本案具体目的。若客户确实只给抽象目标，如实保留并指出缺少什么定义，不能编造更具体的目标。

### 5. 反查后交接
逐项对照原文：漏了什么？加了什么？要求和建议是否混淆？各交付目的是否正确？普通人能否理解？换品牌后仍完全一样是否因为删掉了关键要求？

有依据的明确要求进入摘要，重要未知和我方建议分开。优先询问最多三项会改变任务的决策，不为填表追问。用户认可任务理解不等于客户批准，也不等于洞察成立。

## 输出与停止

默认先给“一句话任务确认”；按复杂度附任务与目的表、关键待确认。背景、来源、规格、判题和研究交接放详细记录，不再强制六栏同时上屏。六项验收见产出标准。

纯执行适配不强加策略；只有业务目标则明确尚待定义的传播任务；目标冲突则陈述冲突并请决策人取舍；信息不足则给有边界的暂定总结，不编完整 Brief。

P0 到此为止，不自动写洞察、口号、策略或剧情。概念阶段不以执行细节压制想象，但明确条件不能删除；资源建议不当作已落实。多智能体评审须另有授权。

## 接入既有工作流

接到纠正或继续既有任务前，核对最新反馈与撤回判断；发生任务偏离或重复错误时执行 [对话纠错机制](references/dialogue-correction.md)。先判断错在任务、推理还是表达，不把所有批评都处理为重新开始。

使用现有登记保存原始输入、当前版本、任务编号、目的、条件与确认依据。P1 按任务研究品牌、产品、竞争、市场、人群及我方相关能力，不只找支持我方假设的材料；发现要说明影响哪项任务。

方法、项目结论、待证假设分别保存。更新项目稿和看板数据后再生成页面；首页只留当前有效判断，历史稿后台保留，实质改题时标记受影响下游稿。仅压缩措辞不自动撤销有效研究。

跨阶段沿用 [创造性推导与维护标准](references/creative-reasoning.md)。理论依据按需读 [研究与取舍](references/theory-and-sources.md)。示例检查与格式校验不代表跨项目成效已验证。
